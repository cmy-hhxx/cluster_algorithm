# 02 L4 归纳（判断"值不值得再拆一层"）

> 占位符：`{{ROOT}}` · `{{RUN}}` · `{{LEAF}}` 待评估的叶子
> L4 是最容易"为了好看而拆"的地方。**默认结论是不拆**，除非三条准入全部通过。

## 1. 输入

`{{RUN}}/l4/{{LEAF}}.jsonl`（该叶子全部条目，字段 `seq/component/label/definition/reason`）。
叶子现状见 `{{ROOT}}/taxonomy/INV_<L1>.md` 里 `{{LEAF}}` 那一行的 definition / include / exclude。

## 2. 三条准入（全部满足才可拆）

| # | 准入 | 判定方法 | 不合格的样子 |
|---|---|---|---|
| A | 规模 ≥ 300 条 | 数一下，别估 | 200 条却硬拆成 4 类，每类 50，统计不稳 |
| B | 能写出**互斥**的 include/exclude | 试着为每个子类写一句排除项，必须指向兄弟 id | 只能写"其他情况"→ 不互斥，不拆 |
| C | 子类对应**不同修复动作** | 问："修 A 类的人会不会顺手把 B 类也修了？" | 会 → 只是同一 bug 的不同表现，不拆 |

补充：若某子类预期占比 < 10%，即使满足三条也并入最接近的子类，避免长尾噪声。

## 3. 三个反模式（出现即判不拆）

1. **按 `component` 拆**：如果叶子内 component 单一，按 component 拆等于没拆。
2. **按 `label` 措辞拆**："返回空"和"返回为空"是同一个类。
3. **按严重度/情绪拆**：分类法不衡量严重度，那是另一个维度（用 tags 或单独打分）。

## 4. 判据的本质

> 拆出来的子类，应该让**两个不同的修复单**成立。
> 如果拆完只能说"这类更严重一点"，那不是分类，是排序。

## 5. 输出

写 `{{RUN}}/l4/{{LEAF}}.plan.json`：

```json
{
  "leaf": "{{LEAF}}",
  "splittable": true,
  "reason": "为什么值得拆（对应哪张修复单）/ 为什么不值得",
  "children": [
    {"id": "{{LEAF}}.1", "name": "≤14 字，动词开头", "plain": "一句人话，≤40 字",
     "definition": "这个子类到底错在哪",
     "include": "什么情况归这里（可判定）",
     "exclude": "什么情况不归这里 → 指向兄弟 id",
     "expected_share": 0.4,
     "fix_hint": "谁会怎么修（一句话，证明可派工）"}
  ]
}
```

- 子类 2–5 个；`expected_share` 之和 ∈ [0.9, 1.1]。
- 不拆时：`"splittable": false, "children": []`，并在 `reason` 写清**什么数据出现时才值得重估**（例："若出现 ≥50 条跨市场同一指标冲突，可再拆地域"）。

## 6. 自检

- 每个 `exclude` 是否指向了具体兄弟 id（不是"其他"）？
- 把 5 条随机条目分别代入，能否**只**落一个子类？
- 三个子类的 `fix_hint` 是否真的不同？相同就合并。
