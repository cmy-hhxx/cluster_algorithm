# 方法论：三轴分类法

> 输入只有归因条目；输出是一棵可下钻、可回溯、可复算的树。
> 本文讲“为什么这样分、怎么计数、怎么验”，不讲部署。部署看 [deploy.md](deploy.md)。

## 1. 聚类单元

- 单元 = **原子归因条目**：归因模型指出的一个具体失效动作，自带 `component`（链路环节）、
  `label`、`definition`、`reason`、`evidence`。
- 一条**只归属一个叶子**。不做多标签，否则计数重复、排名失真。
- 一条同时命中多个问题时，按 **M1→M7 最早失效点**归入靠前的那个（§4）。

## 2. 三轴设计

```text
L1 环节  —— 失败发生在链路哪一段（12 段，由 component 唯一确定，不靠语义猜）
L2 机制  —— 该环节的动作错在哪一层（7 类，跨环节统一口径）
L3 模式  —— 可派工的动作级失效模式（互斥、穷尽）
L4 细分  —— 仅对达标的大叶子下钻（§6）
```

- 当前分类法 **181 叶**（12 环节 × 7 机制；矩阵 67/84 有叶，17 格登记“本环节不适用”）。
- 第一轴是 `component` 而不是“用户现象”：component 给出责任边界，能直接派工。
  同一现象被拆到多个环节的缺点，用**横切标签**（§8）补偿。
- L2 只有 7 类：机制层要能横向比较（“哪一层最普遍”），类别再多就退化成 L3 的同义词。

## 3. 12 个环节

| 段 | 名称 | 判定依据 |
|---|---|---|
| S1 | 取数规划 | `role=planning` 且属取数规划子模型 |
| S2 | 检索规划 | `role=planning` 且属检索规划/实体识别 |
| S3 | 结构化取数 | `role=tool` 的 finquery 与取数技能脚本 |
| S4 | 本地计算 | `role=script` 的沙箱脚本与持仓查询 |
| S5 | 网页检索 | `role=tool` 的 web_search / web_fetch |
| S6 | 客服知识库 | customer_services / CustomerServiceFAQ |
| S7 | 记忆 | aime_memory_read/write、get_user_context、SaveUserProfile |
| S8 | 能力装载 | view_skill/read_file、understand_image |
| S9 | 答案合成 | `role=delivery`（取值/计算/推断/引用/指令遵循） |
| S10 | 请求生成 | `role=request_generation` 的非图表类请求 |
| S11 | 图表与可视化 | display / workflow 的 spec 生成与渲染 |
| S12 | 任务编排 | `family=model` 的泛规划（做几步、什么顺序、补不补前置） |

为什么是 12 段：2026-11 起归因自带 `component_role`，第一轴可以按“职责阶段”切，而不只按
“哪个工具”切。9 段时 826 条“请求生成”摊在 7 个段里，谁都看不出总量；S10 单独成段后是第二大段。
拆分依据始终是**责任边界 + 故障域**：两个团队、两种故障域、三套资源、两种失效、两类独立修法。

两条互斥保证：

1. `component + role → 段` 是精确映射（`components.json` 每个 raw 写法都带 `stage`），
   一条只可能落一个段；
2. 同一现象若两段都有，叶子按段一分为二并**各自命名**，不允许同名，不允许“A 或 B”。

## 4. 7 种机制

| 代码 | 机制 | 判据（该环节的“动作”处于什么状态） |
|---|---|---|
| M1 | 空转未执行 | 没有产出任务所需的最小动作 |
| M2 | 目标错配 | 动作发生了，对象/指标/时段/范围/语义不对 |
| M3 | 执行失败 | 动作在执行层面失败（报错/超时/零行/空返回/截断） |
| M4 | 结果不可用 | 有返回，但内容撑不起任务（不相关/样板/过期/缺字段） |
| M5 | 加工计算错误 | 数据对，但换算/聚合/口径/比较错 |
| M6 | 无依据断言 | 结论缺乏证据，或与已有证据矛盾 |
| M7 | 交付不符 | 形式与完整性不达标（缺项/格式/语言/答非所问） |

**判定优先级**：按 M1 → M7 自上而下匹配，命中即停，取最早失效点。典型边界：

| 边界 | 规则 |
|---|---|
| M1 vs M3 | 没规划/没调用 → M1；调用了但报错零行 → M3 |
| M3 vs M4 | 报错/超时/零行/空 body → M3；有内容但不相关/过期/缺字段 → M4 |
| M2 vs M4 | 请求本身打偏 → M2；请求对、返回错 → M4 |
| M4 vs M5 | 返回的是错东西 → M4；东西对但算错/标错 → M5 |
| M5 vs M6 | 有数据但算错 → M5；没来源却断言 → M6 |
| M6 vs M7 | 说了不该说的 → M6；该说的没说 → M7 |

## 5. L3 准入（三条缺一不可）

1. **互斥**：能写出 `include` 与 `exclude`，排他项必须指向具体兄弟叶，而不是“其他”。
2. **可派工**：开发看到名字知道去改哪。“结果不可用”不合格，“请求字段被静默丢弃”合格。
3. **可复现**：同一 `definition` 下，两个人独立看同一条会落同一个叶子（靠 §9 双盲验）。

禁止兜底桶（“其他/杂项”）。长尾按具体现象命名，样本量小就小，不许合并。

## 6. L4 准入（三条同时满足）

1. 叶子条目数 ≥ **300**；
2. 内部能写出互斥的 include/exclude（不是靠语感切）；
3. 拆出的子类对应**不同的修复动作**（否则只是好看）。

不满足就停在 L3。为了层数整齐去拆小叶子，会制造边界噪声、拉低准确率。
2026-11-23 起 AIME 两棵树各有 **12 个叶子下钻、42 个子类**（fast 39.1% 条目 / 66.7% 的 P0/P1；expert 33.5% / 58.1%）。其余叶子仍停在 L3；不为层数整齐而拆。

## 7. 计数口径

- **主口径 = 会话数**：同一会话在同一叶子只算 1。一个用户踩一次算一次，不被“问题多的会话”放大。
- **附列 = 条目数**：保留原始密度，用于看模型的输出习惯。
- **case = `trace_id`**（2026-11-11 起）：`eval_input` 一行一 trace，一个 case 就是一次提问实例；
  聚类条目、badcase、goldencase 都以它为身份，不再用文件名/行号。
- 三档都要给，但**排序与决策看会话数**。

### badcase / goldencase

每轮在 `CASE_INDEX_ROOT` 下产出两份清单（一行一个 case，按 `request_time` 排序）：

| 文件 | 入选口径 | 用途 |
|---|---|---|
| `badcase_<渠道>.jsonl` | 该 case 有任意 problem 的 `severity ∈ {P0, P1}` | 优先复现/修复 |
| `goldencase_<渠道>.jsonl` | 该 case 的 `problem` 为空 | 回归对照，防止修坏 |

- P2–P4 的 case 不进这两份，只留在树里看分布。
- 字段只有可追溯信息：`bad_case_id / channel / model / question / session_id / trace_id /
  batch_id / request_time / severity / severity_counts / problem_count / first_seen / last_seen`；
  没有行号、没有绝对路径；拿 `trace_id` 回 `eval_input` 就能还原完整 messages。
- 身份索引 `cases_<渠道>.jsonl` 每轮先压一次（`bin/build_cases_index.py`），
  `ingest` 与清单生成都读它。

## 8. 横切标签

一条可多标签，不破坏树的互斥性。当前词表（`taxonomy/tags.json`）：

`时效 / 实体 / 口径 / 单位 / 多标的 / 语言 / 呈现 / 编造 / 缺失 / 失败`

标签由 `taxonomy/leaf_tags.json`（叶子→标签）决定，改标签只改这一张表，不用重跑归类。
它回答“时效类问题一共多少、分布在哪几段”——单靠树答不上。

## 9. 质量协议

| 检查 | 做法 | 通过标准 |
|---|---|---|
| 归属唯一 | 每条恰好 1 个 path，无越界 | 100% |
| 计数自洽 | 子节点之和 = 父节点 | 100% |
| 定位回放 | 抽样 `trace_id/session_id → eval_input` 与原条目比对 | 0 不一致 |
| 边界标记 | 跨组件软约束/兄弟模糊标 `edge` | 记录比例，优先复核 |
| 双盲重标 | 分层抽 600 条（每叶≥3），两方独立标，算 Krippendorff α | α ≥ 0.75；< 0.6 的叶子退回重定义 |
| 分类法自检 | `python3 bin/taxonomy_lint.py`（旧口径/悬空/同名/兜底/矩阵空格） | errors=0 |

2026-10-30 实测（576 条双盲，两人一致 529 条）：

| 指标 | 结果 |
|---|---|
| 两人彼此一致率 | 91.8%（Krippendorff α=0.918） |
| 质量模式 vs 双盲共识（叶子级） | 91.3% |
| 快速模式 vs 双盲共识（叶子级） | 88.1% |
| 机制层一致率 | 97.0%（质量）/ 96.2%（快速） |
| 分类法自检 | 0 errors |

结论：模型与两位独立标注员的一致率（91.3%）已接近两位标注员彼此的一致率（91.8%），
叶子级基本到顶；再提升需要更细的分类法或人工仲裁，而不是换提示词。

## 10. 新工具、新技能怎么进来

不接受“其他/未知”桶。组件路由分两层：

1. **精确表与模式表**：`taxonomy/components.json` 登记精确写法 `{tool, label, role, stage}`；`taxonomy/component_patterns.json` 按正则承接沙箱一次性脚本（如 `/workdir/*.py`）、图像理解多通道（`understand-image-*`）及 `X 请求生成` 等规律性命名。
2. **未命中处理**：
   - **生产原位流水线**（`bin/cluster.py`）：写出 `unregistered.json` 并中断，人工确认责任段后登记重跑，防止新工具静默混入杂项。
   - **可移植模块**（`cluster_pkg`）：默认开启自适应组件登记，结合 `component_role` 与模型路由判定责任段（`S1`–`S12`），持久化写入树目录的 `taxonomy/` 并留存演进日志。

## 11. 演进规则（遇到新失效模式时）

1. 新数据优先按当前分类法叶子归类；模型输出越界 path 时，先走**带合法清单重问**（`PATH_REPAIR`），能收敛到既有叶子的标 `edge` 供复核。
2. 重问后模型明确返回 `NONE`（确无既有叶子可承接）：
   - **生产原位流水线**：写入 `logs/missing_leaf_<渠道>.jsonl` 与 `unresolved_*.json` 留痕并阻断当轮交付，由维护者补叶并过 `taxonomy_lint.py` 后重跑。
   - **可移植模块（`cluster_pkg`）**：默认开启**自适应建叶**，汇总同环节未归类条目归纳互斥新叶（严格挂载在既有 `S1..S12 × M1..M7` 下，禁止“其他/杂项”，排他项指向具体兄弟叶），自动通过 `taxonomy_lint` 零错误校验、刷新 `INV_<L1>.md` 与 `MATRIX.md` 后完成归类，并落盘 `taxonomy_evolution.jsonl`。
3. 历史已归类条目默认保留原判定（按 `(trace_id, problem_index)` 增量复用），避免跨轮次漂移。

## 12. 已知边界

- 只适用于**单轮或可拆到 turn 级**的归因数据；多轮归因需先按 turn 拆开。
- 小样本段的统计稳定性弱，别只看它的排名；`low_sample` 叶子不参与排名。
- 树只描述**失效**，不描述“好答案长什么样”，不能直接当质量评分用。
- 归类依赖模型判断，`edge` 与 α 是它的诚实度刻度，不是装饰。
- 新增叶子只对以后新进的条目生效；历史判定不自动重判（避免漂移）。
